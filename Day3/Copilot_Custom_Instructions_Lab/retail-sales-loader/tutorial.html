LESSON 02What is copilot-instructions.md?

It is a Markdown file containing reusable project guidance for supported Copilot Chat and agent interactions. Instead of repeating “use snake_case and validate CSV rows” in every prompt, save those rules with the repository.

exact relative path
.github/copilot-instructions.md

.github is the folder. copilot-instructions.md is the filename. Markdown is plain text with headings and bullet points; no program executes this file.

Scope: VS Code documents that custom instructions do not apply to inline suggestions as you type. Verify this lesson through Copilot Chat or a supported agent response. Instructions guide behavior; they are not enforced security controls or guaranteed compliance.

LESSON 04Understand load-pattern defaults

A load-pattern default is the behavior the team expects when a prompt does not specify how to load data. It describes data handling, not how Copilot loads the instruction file.

DecisionDefault in this labWhy it matters
Readercsv.DictReaderRows use column names
Encodingutf-8-sigAccepts UTF-8 input with or without BOM
ValidationValidate every row; fail on an invalid rowAvoid silent data loss
MoneyDecimal; finite and positiveAvoid float arithmetic for money
DatesYYYY-MM-DD plus calendar validationReject ambiguous or impossible dates
WritesNo input modificationLoading does not overwrite the source
Return contractValidated records in original orderPredictable downstream behavior

Common patterns in other projects

PatternMeaningInstruction example
AppendAdd rows to a destinationAppend only validated new rows; define duplicate handling.
UpsertInsert new keys and update existing keysUpsert by order_id; document update precedence.
OverwriteReplace existing destination dataUse only for a specifically approved rebuild.
IncrementalLoad changes since a checkpointUse the approved watermark; define late-arriving records and retries.
Do not write “always overwrite” unless it is genuinely the project requirement. A useful default states both the normal behavior and when an exception is permitted.

LESSON 06Write the complete instruction file

Paste this example into .github/copilot-instructions.md. For an active project, adapt each section to the actual stack and policies.

Markdown · .github/copilot-instructions.md
# Copilot instructions for Retail Sales Loader

## Project context
- This project loads a local retail CSV using Python 3.11 or later.
- Use the Python standard library. Do not add packages without a stated need.
- Keep source code in src/, sample CSV files in data/, and tests in tests/.
- Read existing code before proposing changes. Preserve public behavior unless
  the task explicitly requests a change.

## Naming conventions
- Use snake_case for Python functions, variables, and module filenames.
- Use PascalCase for classes and UPPER_SNAKE_CASE for constants.
- Use descriptive names such as load_sales and required_columns.
- Avoid vague names such as process_data, temp, or x for business logic.

## Data-loading defaults
- Use pathlib.Path for filesystem paths.
- For CSV input, use csv.DictReader with encoding="utf-8-sig" and newline="".
- Require these CSV headers: order_id, order_date, amount.
- Validate every row before returning data; report the CSV line number on errors.
- Accept dates only in canonical YYYY-MM-DD format and validate calendar dates.
- Treat amount as INR. Use decimal.Decimal for monetary values.
- Reject non-finite amounts and amounts less than or equal to zero.
- Reject blank order IDs, missing fields, and extra fields in rows.
- Return validated records in input order; raise ValueError for invalid data.
- Raise FileNotFoundError for a missing input path. Never silently skip bad rows.
- Use a path relative to the project location, not a hard-coded Windows user path.
- Default to reading inputs only. Do not overwrite source data.

## What NOT to suggest
- Do not hard-code passwords, tokens, connection strings, or real customer data.
- Do not log secrets or full customer records; report counts and safe error context.
- Do not use eval or exec to parse input.
- Do not use float for money, bare except, or empty exception handlers.
- Do not add pandas, Spark, cloud services, or a database for this local CSV task.
- Do not suggest deleting files or destructive writes as the default load pattern.
- Do not invent APIs, project files, table names, or commands.

## Verification and response
- Use unittest for automated tests. Run: python -m unittest discover -s tests -v
- Cover valid input, missing files, malformed dates, missing headers, and bad amounts.
- Explain changed files, behavior, and validation performed.
- If tests were not run, state that clearly. Do not claim a passing test result.
- If an instruction conflicts with the task or existing architecture, explain
  the conflict before proposing a change.

Each rule is short and independently understandable. Keep instructions concise, consistent, and relevant to most tasks in the repository. Keep tutorial explanations and review history outside the instruction file.

LESSON 07Verify instructions are being used

  2. If needed, open Settings with Ctrl + ,, search for instruction files, and check that automatic use of repository instructions is enabled. Labels vary by installed version.

  4. Use the prompt below without repeating the naming and loading rules.
Copilot Chat prompt
For this project, propose src/sales_loader.py with a load_sales function.
It should load data/sales.csv and print the record count and total amount.

Inspect the response’s references/context details for .github/copilot-instructions.md, where your installed UI exposes them. Then inspect the generated code against the rules. A sentence claiming “I followed the instructions” is not sufficient evidence.

If automatic discovery fails, check the exact path and workspace, save and reload, then retry in a new chat. Manually attaching the file can help diagnosis, but record that the test used manual attachment rather than proving automatic discovery.

LESSON 08Reference implementation and execution

The following is a hand-reviewed reference implementation, not a promise that Copilot will generate identical code. Compare the behavior of your generated code with it.

Python · src/sales_loader.py
import csv
import re
from datetime import date
from decimal import Decimal, InvalidOperation
from pathlib import Path

REQUIRED_COLUMNS = {"order_id", "order_date", "amount"}


def load_sales(csv_path: Path) -> list[dict]:
    csv_path = Path(csv_path)
    records = []
    with csv_path.open("r", encoding="utf-8-sig", newline="") as csv_file:
        reader = csv.DictReader(csv_file)
        headers = reader.fieldnames or []
        if len(headers) != len(set(headers)):
            raise ValueError("Duplicate CSV headers")
        if not REQUIRED_COLUMNS.issubset(headers):
            raise ValueError("Missing required CSV headers")
        for row in reader:
            line_number = reader.line_num
            if None in row or any(value is None for value in row.values()):
                raise ValueError(f"Line {line_number}: incorrect field count")
            order_id = row["order_id"].strip()
            order_date = row["order_date"].strip()
            amount_text = row["amount"].strip()
            if not order_id:
                raise ValueError(f"Line {line_number}: blank order_id")
            if re.fullmatch(r"[0-9]{4}-[0-9]{2}-[0-9]{2}", order_date) is None:
                raise ValueError(f"Line {line_number}: date must use YYYY-MM-DD")
            try:
                parsed_date = date.fromisoformat(order_date)
            except ValueError:
                raise ValueError(f"Line {line_number}: invalid calendar date") from None
            try:
                amount = Decimal(amount_text)
            except InvalidOperation:
                raise ValueError(f"Line {line_number}: invalid amount") from None
            if not amount.is_finite() or amount <= 0:
                raise ValueError(f"Line {line_number}: amount must be finite and positive")
            records.append({
                "order_id": order_id,
                "order_date": parsed_date,
                "amount": amount,
            })
    return records


if __name__ == "__main__":
    project_root = Path(__file__).resolve().parents[1]
    sales = load_sales(project_root / "data" / "sales.csv")
    total_amount = sum((row["amount"] for row in sales), Decimal("0"))
    print(f"Loaded records: {len(sales)}")
    print(f"Total amount (INR): {total_amount:.2f}")

Run on Windows

Open Terminal → New Terminal from the project root. Check Python and run the loader:

PowerShell
python --version
python src/sales_loader.py

If Windows uses the launcher rather than python, use py -3 --version and py -3 src/sales_loader.py. Confirm the interpreter is Python 3.11 or later.

expected output
Loaded records: 3
Total amount (INR): 2449.75

No pip packages are needed for this reference. It resolves the input from the script’s project location and leaves the CSV unchanged. Missing paths raise FileNotFoundError; invalid contents raise ValueError.

LESSON 10Peer review: prepare the submission

Peer review means a colleague checks whether the instructions are accurate, understandable and reflected in generated work. This lesson prepares the material for you to submit through your team’s normal review process.

Reviewer questionAcceptable evidence
Do rules match the actual project?README, existing code and team policy
Are names specific and consistent?Examples in generated code
Are load defaults safe and complete?Input/output contract, invalid data behavior and write rules
Are prohibited suggestions precise?Concrete exclusions and allowed alternatives
Was the instruction file applied?Available references/context evidence plus code inspection
Was verification honest?Actual commands, results and unresolved failures

Submission package

  1. The instruction file or its Git diff.
  2. The exact prompt used and generated code to assess.
  3. Actual execution/test evidence, with failures retained.
  4. The completed review checklist and open questions.

Example reviewer comment: “The rule says dates must use YYYY-MM-DD, but code accepts other formats. Add strict format validation and a test for 01/10/2026.”

Example author response: “Added a format check before date parsing and a regression test; recorded the new test result.”

Distinguish guidance from enforcement. “Do not log secrets” expresses intent; logging controls, code review and tests provide concrete checks.

LESSON 11Commit and submit for review

In an active Git repository, review its workflow first and create a branch if that is your team’s practice. For a new standalone lab, run git init once.

PowerShell · instructions commit
git status --short
git switch -c docs/copilot-project-instructions
git add .github/copilot-instructions.md
git diff --cached
git commit -m "Document project conventions for Copilot"

Commit sample code and review records only if they belong in this repository. For this standalone lab:

PowerShell · optional lab files
git add README.md data/sales.csv src/sales_loader.py docs/peer-review.md
git diff --cached
git commit -m "Add custom instructions lab and review evidence"

Add tests/test_sales_loader.py separately after it exists and has been reviewed. Do not commit temporary outputs, private data or credentials.

Submit through your existing team process

For a repository with a configured remote and a GitHub PR workflow, push the branch using your actual remote name, then open a pull request with your team as reviewers. For classroom work, share the instruction file and review evidence through the trainer’s designated channel.

optional push · replace YOUR_REMOTE_NAME
git push -u YOUR_REMOTE_NAME docs/copilot-project-instructions

PR title: Add Copilot project conventions and CSV loading defaults.

PR description: “Adds repository instructions covering Python naming, CSV validation, Decimal money handling and prohibited suggestions. Includes the prompts, generated code and verification evidence used to assess the guidance. Please review policy accuracy and rule compliance.”

The reviewer completes the decision in the review record. Address requested changes, retest affected behavior, commit the revision and request another review. This tutorial does not send a review request or submit a PR on your behalf.
