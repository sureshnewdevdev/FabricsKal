01. What you will build

Create a retail sales analytics solution that moves source records through three quality layers and produces daily revenue for Power BI.

BronzeCapture all 8 raw sales records, including duplicates and invalid values.
SilverKeep 5 valid, unique orders after data quality checks.
GoldSummarize valid orders into daily business KPIs.
Prerequisites: Microsoft Fabric workspace with an active Fabric capacity or trial that supports Lakehouse and Spark notebooks; permission to create items. A Power BI report may require additional permissions or licensing.

Tools: Fabric Lakehouse, Fabric Notebook (PySpark), optional Data Factory pipeline, and Power BI. The core lab uses a single Lakehouse to keep setup simple.

02. Understand the architecture

Source: Retail order CSV 8 sample records
↓ Ingest
BRONZE · raw_orders Preserve source values and add ingestion metadata
↓ PySpark cleaning + validation
SILVER · clean_orders Typed, valid, deduplicated orders
↓ PySpark aggregation
GOLD · daily_sales Daily revenue and order count
↓ Analyze
Power BI Daily sales trends and KPIs

Key concept: Bronze, Silver and Gold describe increasing data quality and business readiness. They are not separate paid Fabric products. Here, each layer is a Delta table within one Lakehouse.

05. Bronze — preserve raw data

Goal: retain the exact original field values, including bad records, for audit and reprocessing. Add an ingestion timestamp; do not silently discard invalid data.

Notebook cell 1 — create and save Bronze

from pyspark.sql import functions as F

raw_rows = [
    ("O101", "2026-10-01", "Asha",  "Laptop",    "1",  "50000"),
    ("O102", "2026-10-01", "Ravi",  "Mouse",     "2",  "500"),
    ("O103", "2026-10-02", "Meena", "Keyboard",  "1",  "1500"),
    ("O104", "2026-10-02", "John",  "Monitor",   "1",  "10000"),
    ("O102", "2026-10-01", "Ravi",  "Mouse",     "2",  "500"),
    ("O105", "2026-10-02", "Sara",  "USB Cable", "-1", "300"),
    ("O106", "2026-10-03", "Dev",   "Webcam",    "1",  "2000"),
    ("O107", "2026-10-03", "Priya", "Headset",   "1",  "abc")
]

cols = ["order_id", "order_date", "customer", "product",
        "quantity", "unit_price"]

bronze = (spark.createDataFrame(raw_rows, cols)
          .withColumn("ingested_at", F.current_timestamp()))

bronze.write.format("delta").mode("overwrite").saveAsTable("bronze_orders")
print("Bronze count:", spark.table("bronze_orders").count())
display(spark.table("bronze_orders"))
Expected: Bronze count = 8. Under your Lakehouse's Tables area, you should see bronze_orders. The original price abc remains a string.

Why strings? Landing data as text avoids accidental loss of malformed values before validation.

06. Silver — validate, clean and deduplicate

Goal: convert data types, remove exact duplicates, and separate invalid records for review. The business rule is that quantity and unit price must both be positive.

Notebook cell 2 — create Silver and rejected-records tables

from pyspark.sql import functions as F

source = spark.table("bronze_orders")

# Convert strings to appropriate types; invalid numeric values become NULL.
typed = (source
    .withColumn("sale_date", F.to_date("order_date", "yyyy-MM-dd"))
    .withColumn("qty", F.expr("try_cast(quantity as int)"))
    .withColumn("price", F.expr("try_cast(unit_price as decimal(12,2))")))

# Remove exact duplicate business records (ignore ingestion metadata).
unique = typed.dropDuplicates([
    "order_id", "order_date", "customer", "product",
    "quantity", "unit_price"
])

valid_rule = (
    F.col("order_id").isNotNull() &
    F.col("sale_date").isNotNull() &
    F.col("qty").isNotNull() & (F.col("qty") > 0) &
    F.col("price").isNotNull() & (F.col("price") > 0)
)

valid = unique.filter(valid_rule)
rejected = unique.filter(~valid_rule)

silver = (valid
    .withColumn("sales_amount", F.col("qty") * F.col("price"))
    .select("order_id", "sale_date", "customer", "product",
            "qty", "price", "sales_amount"))

silver.write.format("delta").mode("overwrite").saveAsTable("silver_orders")
rejected.write.format("delta").mode("overwrite").saveAsTable("rejected_orders")

print("Silver count:", spark.table("silver_orders").count())
print("Rejected count:", spark.table("rejected_orders").count())
display(spark.table("silver_orders"))
Expected: Silver = 5 unique valid orders; rejected = 2 invalid orders (O105 and O107). One duplicate O102 is removed.

Production note: This demonstration uses exact-row deduplication. Real systems should define a business key and a deterministic latest-record rule (for example, event timestamp + source sequence). Preserve rejected records and rejection reasons for remediation.

07. Gold — business-ready daily revenue

Goal: aggregate validated sales by date. A business user can now query daily revenue without repeating cleaning logic.

Notebook cell 3 — aggregate Gold

from pyspark.sql import functions as F

gold = (spark.table("silver_orders")
    .groupBy("sale_date")
    .agg(
        F.countDistinct("order_id").alias("total_orders"),
        F.sum("sales_amount").alias("total_revenue")
    )
    .orderBy("sale_date"))

gold.write.format("delta").mode("overwrite").saveAsTable("gold_daily_sales")
display(spark.table("gold_daily_sales").orderBy("sale_date"))

10. Validate every layer

Always verify row counts, rejected data, and revenue totals rather than assuming a successful notebook run means correct business results.

from pyspark.sql import functions as F

assert spark.table("bronze_orders").count() == 8
assert spark.table("silver_orders").count() == 5
assert spark.table("rejected_orders").count() == 2
assert spark.table("gold_daily_sales").count() == 3

revenue = (spark.table("gold_daily_sales")
    .agg(F.sum("total_revenue").alias("revenue"))
    .first()["revenue"])
assert float(revenue) == 64500.0
print("All medallion validation checks passed!")

Additional production checks include null-rate thresholds, schema drift, uniqueness of business keys, reconciliation against source totals, data freshness, and access controls for sensitive fields.

11. Troubleshooting

Table not found: bronze_orders

Run the Bronze cell first, verify that the notebook has the intended default Lakehouse, and confirm the table appears under Tables.

No Fabric capacity or Spark session available

Confirm workspace capacity assignment and permissions. Trial access and workload availability are tenant-dependent.

Why use try_cast instead of cast?

try_cast returns null for malformed numeric values, allowing us to reject them explicitly. A strict cast may raise an exception in some Spark configurations.

Why are only five rows in Silver?

Eight source rows minus one exact duplicate and two invalid records equals five valid rows.

Can I use three separate Lakehouses?

Yes. Separate Bronze, Silver and Gold Lakehouses can improve isolation and permission management. This lab uses three Delta tables in one Lakehouse for easier setup.

Can I use SQL or Dataflow Gen2 instead of PySpark?

Yes. Dataflow Gen2 is suitable for visual transformations; SQL-based approaches are also possible. PySpark is used here to demonstrate transformations and validation transparently.
