Learning outcomes

Set up an approved Copilot environment, define project conventions, create reusable prompts, follow Git/PR workflow, connect Fabric through approved Git integration, and validate AI-generated changes with human oversight.

Continuous case study: insurance policy data

Policy source→Fabric Bronze→Silver validation→Gold model→Power BI

Copilot supports the developer across these stages; it does not replace data governance, review or testing.

Pre-work: Organizational Copilot entitlement, approved Git repository, Fabric workspace access, sample repo, VS Code and Git. Follow organization policies. Do not paste confidential insurance data into an unapproved AI tool.

Topic 1 · 35 minutes · Day 1

Installation & Initial Setup

1. What and why?

Install VS Code Stable, Git and the approved GitHub Copilot extensions. Sign in with your organization-authorized account; confirm entitlement and extension policy.

2. Step-by-step demonstration

Open VS Code → Extensions (Ctrl+Shift+X) → install GitHub Copilot (and GitHub Copilot Chat if offered separately). Use Accounts → Sign in to GitHub. Open a trusted sample repository, then test Copilot Chat with a non-sensitive question.

3. Trainer demonstration / prompt / code

Ask: “Explain the folders in this sample BI repository. Do not change any files.”

4. Hands-on assignment

Topic 2 · 45 minutes · Day 1

Settings That Actually Matter

1. What and why?

Differentiate user settings from workspace settings. Workspace .vscode/settings.json can standardize editor behavior, but it is not a data-loss prevention control.

2. Step-by-step demonstration

Create .vscode/settings.json. Add settings below; review actual Copilot setting support in the installed extension version. Commit settings after peer review.

3. Trainer demonstration / prompt / code

{"editor.formatOnSave": true, "files.trimTrailingWhitespace": true, "github.copilot.enable": {"*": true, "plaintext": false, "json": false}}
{"editor.formatOnSave": true, "files.trimTrailingWhitespace": true, "github.copilot.enable": {"*": true, "plaintext": false, "json": false}}

4. Hands-on assignment

Commit workspace settings and explain why secret scanning, access controls and exclusion policies are still needed.

5. Risk, limitation & troubleshooting

Never assume disabling suggestions for JSON blocks all Chat/agent access to that file. Use approved enterprise policy and avoid opening secrets.

Topic 3 · 60 minutes · Day 1

Custom Instructions (copilot-instructions.md)

1. What and why?

Repository instructions make naming conventions, business rules, and review expectations visible to Copilot. Treat them as guidance, not enforceable security policy.

2. Step-by-step demonstration

Create .github/copilot-instructions.md. Document SQL naming, load semantics, testing expectations and prohibited actions. Ask a peer to challenge ambiguities.

3. Trainer demonstration / prompt / code

## Project rules
- Use snake_case for SQL columns.
- Preserve existing FULL vs INCREMENTAL load semantics.
- Never invent source-to-target mappings.
- Never include customer PII in examples.
- Ask for confirmation before changing schema or SCD2 rules.
- Provide validation SQL for every generated transformation.
## Project rules - Use snake_case for SQL columns. - Preserve existing FULL vs INCREMENTAL load semantics. - Never invent source-to-target mappings. - Never include customer PII in examples. - Ask for confirmation before changing schema or SCD2 rules. - Provide validation SQL for every generated transformation.

4. Hands-on assignment

Peer-reviewed instructions file committed to the sample repository.

5. Risk, limitation & troubleshooting

Verify that the instruction file is recognized by the current IDE/Copilot version; test with a scoped prompt and inspect output.

Topic 4 · 50 minutes · Day 1

Skills — Reusable Prompt / Context Files

1. What and why?

Reusable prompts standardize weekly work. A prompt file is a reusable instruction; an agent skill is a different, tool-specific packaging concept. Availability and conventions depend on installed versions.

2. Step-by-step demonstration

Create .github/prompts/weekly-etl-review.prompt.md and define scope, required inputs, outputs, and review criteria. Ask a teammate to run it unchanged.

3. Trainer demonstration / prompt / code

---
description: Review weekly ETL changes
---
Review the selected ETL changes for data loss, duplicate keys, FULL/INCREMENTAL load behavior, null handling and performance.
Return: risks, evidence, tests to run and questions for the developer. Do not modify code.
--- description: Review weekly ETL changes --- Review the selected ETL changes for data loss, duplicate keys, FULL/INCREMENTAL load behavior, null handling and performance. Return: risks, evidence, tests to run and questions for the developer. Do not modify code.

4. Hands-on assignment

Commit reusable prompt and capture teammate feedback.

5. Risk, limitation & troubleshooting

Do not put credentials, customer records or unapproved data in reusable context files.

Topic 5 · 50 minutes · Day 1

Git / DevOps Connection

1. What and why?

Git tracks changes; pull requests provide review, traceability and a route into standard CI/CD. AI-authored changes require the same scrutiny as human-authored changes.

2. Step-by-step demonstration

Open sample repo → Source Control → create feature branch → make one small change → inspect diff → stage and commit → push → create PR in your organization’s Git platform.

3. Trainer demonstration / prompt / code

git checkout -b feature/policy-validation
git status
git add .github/copilot-instructions.md
git commit -m "docs: add ETL Copilot guidance"
git push -u origin feature/policy-validation
git checkout -b feature/policy-validation git status git add .github/copilot-instructions.md git commit -m "docs: add ETL Copilot guidance" git push -u origin feature/policy-validation

4. Hands-on assignment

Open a PR with a Copilot-drafted description, then correct it manually against the diff.

5. Risk, limitation & troubleshooting

Never let AI claim tests passed unless their actual outputs were checked.

Topic 6 · 30 minutes · Day 2

Tokens & Effective Token Use

1. What and why?

Tokens are pieces of text processed by a model; more context is not always better. Narrowly scoped files often reduce noise and incorrect assumptions.

2. Step-by-step demonstration

Ask the same question with a 500+ line file, a short extracted function, and an explicit file reference (@file if supported). Compare relevance, assumptions and review effort.

3. Trainer demonstration / prompt / code

Compare FULL-load handling in the selected stored procedure only. Cite the relevant lines, identify missing context, and do not infer other procedures.
Compare FULL-load handling in the selected stored procedure only. Cite the relevant lines, identify missing context, and do not infer other procedures.

4. Hands-on assignment

Record a three-column comparison: context supplied, answer quality, and unsupported assumptions.

5. Risk, limitation & troubleshooting

Exact token counts, model limits and billing vary by product, model and organization.

3. Trainer demonstration / prompt / code

Topic 8 · 45 minutes · Day 2

Fabric Workspace Connection

1. What and why?

Microsoft Fabric Git integration links supported workspace items to a configured repository and branch. Workspace permissions, tenant settings and supported item types matter.

2. Step-by-step demonstration

In Fabric open the approved workspace → Workspace settings → Git integration (label may vary) → connect the approved Git provider/repo/branch → inspect changes → commit/update and sync. Use a disposable sample item.

3. Trainer demonstration / prompt / code

Document: repository/branch, initial state, changed item, Git commit, Fabric sync result and one failure or conflict.
Document: repository/branch, initial state, changed item, Git commit, Fabric sync result and one failure or conflict.

4. Hands-on assignment

Evidence of pull/change/push/sync round trip.

5. Risk, limitation & troubleshooting

Not all Fabric items support Git equally; avoid assuming a sync deploys every object or all underlying data.

Topic 9 · 20 minutes · Day 2

Authentication & Permissions Mechanics

1. What and why?

Separate identity authentication from authorization. A Git repo role does not automatically grant Fabric workspace access, and vice versa.

2. Step-by-step demonstration

Prepare an onboarding checklist covering organization identity, Copilot entitlement, repo read/write, PR policy, Fabric workspace role, Git integration permissions and secret access restrictions.

3. Trainer demonstration / prompt / code

Review access by least privilege; confirm branch protection and approval requirements before changes.
Review access by least privilege; confirm branch protection and approval requirements before changes.

4. Hands-on assignment

Permission checklist for a new team member.

5. Risk, limitation & troubleshooting

Never grant workspace Admin or broad secrets access simply to resolve an onboarding error.

Topic 10 · 20 minutes · Day 2

When NOT to Use AI

1. What and why?

Avoid unsupervised AI for decisions that can affect regulated customer data, financial outcomes, or irreversible production changes.

2. Step-by-step demonstration

Identify three recent situations in which unsupervised generation is inappropriate: PII exposure, incorrect FULL-load semantics, and production deletion/overwrite.

3. Trainer demonstration / prompt / code

For each case record risk, human approval owner, allowed AI assistance and independent validation required.
For each case record risk, human approval owner, allowed AI assistance and independent validation required.

4. Hands-on assignment

Three scenarios with a written risk statement.

5. Risk, limitation & troubleshooting

AI can help draft checks, but it cannot replace accountable human sign-off.

Topic 11 · 25 minutes · Day 2

Do's and Don'ts for AI in Data Work

1. What and why?

Use AI to propose code, tests and explanations; do not treat output as evidence of correctness. The schedule highlights an insurance FULL-load bug as an example.

2. Step-by-step demonstration

Create a one-page card: DO use synthetic data; DO check row counts and lineage; DO review joins; DON’T paste secrets; DON’T change FULL to incremental implicitly; DON’T bypass approvals.

3. Trainer demonstration / prompt / code

Scenario: policy source has 10,000 rows. An incorrect FULL-load implementation appends instead of replacing. Ask Copilot to generate reconciliation tests and manually verify counts.
Scenario: policy source has 10,000 rows. An incorrect FULL-load implementation appends instead of replacing. Ask Copilot to generate reconciliation tests and manually verify counts.

4. Hands-on assignment

Peer-reviewed insurance-data Do/Don’t card.

5. Risk, limitation & troubleshooting

A FULL-load strategy is system-specific; replacing data can also be unsafe if history preservation is required.

Topic 12 · 25 minutes · Day 2

Validating AI-Generated Code

1. What and why?

Validation includes correctness, security, data quality, performance and rollback readiness. A successful execution alone does not establish correctness.

2. Step-by-step demonstration

Use synthetic policy rows: duplicate policy ID, NULL premium, cancelled policy, changed premium and an empty source batch. Test a generated stored procedure against expected outputs.

3. Trainer demonstration / prompt / code

SELECT PolicyId, COUNT(*) AS cnt FROM dbo.PolicySilver GROUP BY PolicyId HAVING COUNT(*) > 1;
SELECT COUNT(*) AS row_count FROM dbo.PolicySilver;
-- Add business-specific checks for nulls, load type and history.
SELECT PolicyId, COUNT(*) AS cnt FROM dbo.PolicySilver GROUP BY PolicyId HAVING COUNT(*) > 1; SELECT COUNT(*) AS row_count FROM dbo.PolicySilver; -- Add business-specific checks for nulls, load type and history.

4. Hands-on assignment

Checklist with pass/fail evidence, expected vs actual outcomes and reviewer approval.

5. Risk, limitation & troubleshooting

Never run generated destructive SQL in production before isolated testing, backups and authorization.
