Make Copilot useful to the whole team

Settings choose editor behavior. Instructions communicate project rules. Reusable prompts and skills capture repeatable work. Git and pull requests turn an AI suggestion into a reviewed, traceable change.

src/sales_etl.py
"""Small local CSV ETL lab; no cloud access or credentials required."""
import csv
from decimal import Decimal
from pathlib import Path


def is_valid_sale(row):
    """Baseline rule: amount must be positive. Improve this in Module 5."""
    return Decimal(row["amount"]) > 0


def load_sales(source_path):
    with Path(source_path).open(newline="", encoding="utf-8") as source:
        return list(csv.DictReader(source))


def build_daily_sales(rows):
    totals = {}
    for row in rows:
        if is_valid_sale(row):
            day = row["order_date"]
            totals[day] = totals.get(day, Decimal("0")) + Decimal(row["amount"])
    return [
        {"order_date": day, "total_sales": f"{total:.2f}"}
        for day, total in sorted(totals.items())
    ]


def write_daily_sales(rows, target_path):
    target = Path(target_path)
    target.parent.mkdir(parents=True, exist_ok=True)
    with target.open("w", newline="", encoding="utf-8") as destination:
        writer = csv.DictWriter(destination, fieldnames=["order_date", "total_sales"])
        writer.writeheader()
        writer.writerows(rows)


if __name__ == "__main__":
    project_root = Path(__file__).resolve().parents[1]
    sales = load_sales(project_root / "data" / "sales.csv")
    result = build_daily_sales(sales)
    write_daily_sales(result, project_root / "output" / "daily_sales.csv")
    print(result)
tests/test_sales_etl.py
import unittest
from src.sales_etl import build_daily_sales, is_valid_sale


class SalesEtlTests(unittest.TestCase):
    def test_positive_amount_is_valid(self):
        self.assertTrue(is_valid_sale({"amount": "1500.00"}))

    def test_zero_amount_is_invalid(self):
        self.assertFalse(is_valid_sale({"amount": "0.00"}))

    def test_daily_totals_are_sorted(self):
        rows = [
            {"order_date": "2026-10-02", "amount": "2500.00"},
            {"order_date": "2026-10-01", "amount": "1500.00"},
            {"order_date": "2026-10-01", "amount": "500.00"},
            {"order_date": "2026-10-02", "amount": "0.00"},
        ]
        self.assertEqual(build_daily_sales(rows), [
            {"order_date": "2026-10-01", "total_sales": "2000.00"},
            {"order_date": "2026-10-02", "total_sales": "2500.00"},
        ])


if __name__ == "__main__":
    unittest.main()

2. Settings That Actually Matter

2.1 Understand scope before changing a value

User settings express personal preferences across workspaces. Workspace settings belong to the current project and can be shared through Git. In a single-folder repository, place them in .vscode/settings.json. In a multi-root workspace, also check the .code-workspace file and folder-level settings. An organization policy or other scope may affect the effective value; always check VS Code’s displayed setting and behavior.

Example: You want AI suggestions in Python source, but no inline suggestions in JSON configuration or lab secret files. Share this rule as repository configuration so contributors receive it when they open this folder.

2.2 Know exactly what is disabled

ControlEffectLimit
github.copilot.enableEnables/disables inline suggestions by VS Code language ID. [S1]Not a filename exclusion list. A key like "*.json" is incorrect.
files.associationsMaps matching files to a language mode. [S2]Used here to classify selected secret patterns as plaintext; changes editor language features.
github.copilot.nextEditSuggestions.enabledTurns off next-edit suggestions for this lab. [S8]Separate from chat and agent tool access.
.gitignoreKeeps matching untracked files out of ordinary Git addsDoes not remove already tracked files and is not a Copilot privacy guarantee.
Content exclusionSeparate GitHub feature for eligible managed plans. [S7]GitHub documents that CLI and IDE agent mode do not support it. Check supported surfaces before relying on it.
The lab objective is to disable inline suggestions for JSON and mapped secret files. These settings do not guarantee that Copilot Chat or an agent cannot read those files. Keep actual credentials outside the AI-accessible training workspace. Test only with dummy values. Hiding a file with Explorer or search exclusions is also not an access boundary.

2.3 Guided GUI steps

  1. Open the cloned repository folder in VS Code.
  2. Press Ctrl+Shift+P, search Preferences: Open Workspace Settings (JSON) and select it.
  3. If needed create .vscode/settings.json in Explorer.

  5. Save. Open Settings with Ctrl+,, select Workspace and search the setting name to inspect its value.
.vscode/settings.json
{
  "github.copilot.enable": {
    "*": true,
    "json": false,
    "jsonc": false,
    "plaintext": false
  },
  "github.copilot.nextEditSuggestions.enabled": false,
  "files.associations": {
    ".env": "plaintext",
    ".env.*": "plaintext",
    "*.secrets": "plaintext",
    "**/secrets/**": "plaintext"
  },
  "github.copilot.chat.codeGeneration.useInstructionFiles": true
}

2.4 Read the file line by line

  • "*": true allows inline suggestions for other language modes.
  • "json": false covers JSON. "jsonc": false also covers JSON with Comments, often used for VS Code configuration.
  • "plaintext": false disables inline suggestions in all plain-text documents in this workspace, including the mapped secret patterns.
  • .env, .env.*, *.secrets and files under secrets/ are associated with Plain Text. The patterns are a lab convention, not an exhaustive inventory of sensitive files.
  • Next-edit suggestions are turned off to reduce a second suggestion surface during verification.
  • useInstructionFiles enables project instructions in the Local-agent workflow. Current Copilot Agent Host sessions discover the repository file through their harness. [S3]

3. Custom Instructions: copilot-instructions.md

3.1 Why instructions help

A chat request such as “write an ETL function” leaves many choices open: naming, libraries, monetary types, load behavior and checks. A repository instructions file records the team’s defaults so contributors do not need to restate them in every request. These are contextual guidance for the model; tests, code review and technical controls still verify the result.

Place the project-wide file at .github/copilot-instructions.md. Current VS Code supports it for Copilot project guidance; discovery depends on the selected session/harness. Targeted .instructions.md files can add narrower rules. [S3]

3.2 Turn vague advice into observable rules

Vague guidanceReviewable guidance
Use good namesUse snake_case for Python functions and CSV columns.
Load safelyRefresh only output/daily_sales.csv; never overwrite the source.
Be secureUse placeholders; do not read .env or secrets/ in this lab.
Make quality codeKeep extraction/validation/aggregation/writing separate and test changed behavior.
Follow architecturePreserve public function names; use Decimal for monetary values.
Test everythingRun the documented unittest command and report actual results or Not run.

3.3 Clarify “load-pattern defaults”

A load pattern describes how data reaches its destination. It is separate from the AI “loading” an instructions file. For this local sample, a full refresh replaces the generated summary CSV on each run. A future database workflow needs additional decisions.

PatternExampleQuestions to answer
Full refreshRegenerate a small daily report from the complete CSVIs the output disposable? Can readers tolerate replacement? Is the input complete?
AppendAdd immutable new events to a history tableHow will retries avoid duplicates? What uniquely identifies an event?
Incremental merge/upsertApply inserts and corrections using order_idWhat are the business key, watermark, late-arrival policy, deletes and retry behavior?
A deterministic refresh produces the same output for the same input. An idempotent database load produces the intended state even after a retry. Appending a file twice is usually not idempotent. The local tutorial demonstrates deterministic output; it does not implement transactional table replacement or a production watermark.

  1. Create .github under the repository root.
  2. Create copilot-instructions.md inside it.
  3. Paste the file below, then verify every path and command against your current project.

.github/copilot-instructions.md
# Sales ETL project instructions

## Project and commands
- This is a local Python 3.11+ CSV ETL training project.
- Use the Python standard library; no extra dependencies by default.
- Source: src/sales_etl.py. Tests: tests/test_sales_etl.py.
- From the repository root run: python -m unittest discover -s tests -v.
- Demo execution: python src/sales_etl.py.
- Input is synthetic data/sales.csv. Output is generated output/daily_sales.csv.

## Naming and design
- Use snake_case for functions, variables, modules and CSV column names.
- Use PascalCase for classes and UPPER_SNAKE_CASE for constants.
- Keep extraction, validation, aggregation and writing separate.
- Keep existing public function names and output column names unchanged.
- Use Decimal for monetary values, not float.

## Load-pattern defaults
- For this small local lab, use a full deterministic refresh of the generated CSV.
- The same input must produce the same sorted daily totals.
- Never overwrite the input file.
- Do not introduce incremental loading without an agreed business key,
  watermark, update/delete behavior and retry strategy.
- For a future database or Fabric target, propose staging and validation before
  a replace or merge; do not translate this CSV overwrite into a table truncate.

## What NOT to suggest
- No real tokens, passwords or customer data in code, prompts or examples.
- Do not read .env, .env.*, secrets/ or *.secrets; .env.example is a placeholder.
- No network calls, cloud provisioning or paid services for this exercise.
- Do not disable validation, tests or review controls to make a check pass.
- No unrelated refactoring, new frameworks, table truncation or force pushing.

## Verification and communication
- When changing behavior, add focused tests for that behavior.
- Run the documented tests if tools are available and show actual results.
- If commands were not run, state "Not run"; never invent test results.
- Explain assumptions and any change to rejected-row handling.
- Draft commit messages and PR descriptions from the actual diff.
- Stop before pushing, opening a PR or merging unless the user requested it.

4.2 Weekly task: ETL health review

Every week the team checks validation rules, financial precision, refresh behavior and coverage. The output must cite files and actual test evidence. The task should not rewrite the pipeline or silently publish changes. A reusable file reduces repeated typing and keeps the review method consistent.

Reusable contract: inputs → procedure → boundaries → output format → missing-evidence handling. A prompt without inputs invites assumptions; one without an output format makes teammate results harder to compare.

5.4 Reference implementation

Replace the baseline validator with this function and extend the existing decimal import. Keep the rest of the ETL unchanged.

src/sales_etl.py • replacement validator
from decimal import Decimal, InvalidOperation


def is_valid_sale(row):
    """Accept a finite positive decimal amount; reject unusable inputs."""
    raw_amount = row.get("amount")
    if raw_amount is None:
        return False
    try:
        amount = Decimal(str(raw_amount).strip())
    except (InvalidOperation, ValueError):
        return False
    return amount.is_finite() and amount > 0
tests/test_sales_etl.py • add methods inside SalesEtlTests
    def test_missing_and_none_amounts_are_invalid(self):
        for row in ({}, {"amount": None}):
            with self.subTest(row=row):
                self.assertFalse(is_valid_sale(row))

    def test_unusable_amounts_are_invalid(self):
        for amount in ("", "   ", "abc", "NaN", "Infinity", "-Infinity", "-1"):
            with self.subTest(amount=amount):
                self.assertFalse(is_valid_sale({"amount": amount}))

    def test_positive_amount_with_spaces_is_valid(self):
        self.assertTrue(is_valid_sale({"amount": " 12.50 "}))

Expected after adding these three methods: 6 tests pass; the input sample still produces ₹2,000.00 and ₹2,500.00 daily totals. This validator follows the stated lab requirements; date validation, duplicate-order handling, rejected-row audit storage and locale-specific amounts are further work.

Interview questions with model answers

What is the difference between user and workspace settings?

User settings are personal defaults. Workspace settings apply to the project scope and can be committed for contributors. Check the effective value when scopes or policies overlap.

Does disabling Copilot for JSON keep JSON out of chat?

No. github.copilot.enable controls inline suggestions by language. Chat context and agent tools are separate surfaces.

Why should load defaults be in project instructions?

They reduce ambiguity about refresh, append or merge behavior. The actual implementation still needs validation, tests and review.

What makes an instruction useful?

It is project-specific, concrete, consistent, concise and checkable against files, behavior or commands.

How is a prompt file different from a skill?

A prompt file stores an explicitly invoked task in supported Local sessions. A skill is a directory with SKILL.md, discovery metadata and optional resources for a reusable workflow.

Does a weekly prompt run automatically every week?

No. A saved procedure does not create a scheduler or automation.

Why inspect git diff --cached?

It is the exact staged patch for the next commit, which may differ from all working-tree changes.

Can Copilot generate a PR description?

Yes, through supported UI actions or a chat request with the diff. Review the draft for actual behavior, evidence and scope.

Does opening a PR deploy the code?

No. It proposes a change. Merge and deployment depend on repository workflows and permissions.

What should the report say if tests could not run?

Not run, with the reason and the relevant command. Never substitute an expected result for evidence.
