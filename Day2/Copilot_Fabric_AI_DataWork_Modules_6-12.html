6Tokens & Effective Token Use

0:00 – 0:30 · 30 min · 10 min concept + 20 min lab

6.1 Why this matters more in 2026

Tokens used to be a "quality" topic — too much context makes answers vaguer. Since 1 June 2026 they are also a cost topic. GitHub replaced premium requests with GitHub AI Credits, and credits are consumed according to token usage (input, output and cached tokens) at each model's published rate. One credit = US $0.01. So a sloppy prompt over a 900-line file is now visibly more expensive than a scoped one.

6.2 Concepts in plain words

TermWhat it means for a data engineer
TokenA chunk of text the model reads/writes. Rough rule: ~4 characters of English ≈ 1 token. SQL and code tokenise worse (brackets, underscores, long identifiers like stg_policy_premium_txn split into several tokens).
Input tokensEverything sent to the model: your prompt + chat history + attached files + whatever Copilot pulls in automatically (active editor, selection, workspace search results).
Output tokensWhat the model writes back. Usually priced higher than input. "Rewrite the whole file" = lots of output tokens.
Cached tokensRepeated context the provider can reuse cheaply. Long chat threads keep resending history — cheaper when cached, but still not free.
Context windowThe maximum the model can "see" at once. Hitting it means older history or parts of files are dropped or summarised — answers start ignoring earlier instructions.

6.3 The three ways to give Copilot context (VS Code)

ModeHowWhat actually gets sent
A · Whole file (unscoped)Open the 500+ line file, put the cursor anywhere, ask in Chat with nothing selected.Copilot decides which parts of the active file (and possibly other open tabs) to include. You don't control it.
B · Selection-scopedHighlight only the relevant 30–60 lines, then ask (or use #selection).Your selection, plus a bit of surrounding context.
C · Reference-scopedNew chat, no editor focus. Type #file: and pick a small file, or #sym/#selection.Exactly the files/symbols you reference — the most predictable.
Gotcha — "@file" vs "#file" In VS Code Copilot Chat, @ picks a participant (@workspace, @terminal, @vscode) and # attaches context (#file, #selection, #codebase). Learners often type @file — it does nothing useful. The lab's "@file-scoped" run means #file:. You can also drag a file into the chat box or use the paperclip Add Context button.
Gotcha — @workspace / #codebase are the expensive ones They search the whole repo and stuff matches into the prompt. Great for "where is X used?", wasteful for "explain this function".

6.4 Lab — same question, three contexts (20 min)

Use the same question every time. Pick one with a checkable right answer. Suggested for an insurance stored procedure:

PROMPT — use word-for-word in all 3 runs
In the procedure that loads policy premium data, explain exactly how the
procedure decides between a FULL load and an INCREMENTAL load.
List: (1) the parameter or variable that controls it, (2) its default value,
(3) the line(s) where the target table is truncated or deleted,
(4) what happens if the source returns zero rows.
Answer in a numbered list. Do not rewrite the code.
  1. Prepare. Open your 500+ line file. Close every other editor tab (Ctrl+K W). Note the model selected in the chat model picker — keep it the same for all three runs.
  2. Count the tokens first so you can compare numbers, not feelings. Run the estimator below on the whole file and on the 40-line excerpt (save the excerpt as excerpt.sql).
  3. Run A — whole file. New chat (Ctrl+L / the + button). Cursor in the file, nothing selected. Paste the prompt. Expand "Used n references" under the answer and note what was attached.
  4. Run B — selection. New chat. Select only the load-decision block (~30–60 lines). Paste the same prompt.
  5. Run C — #file. Save the excerpt as its own small file. New chat, click outside the editor, type #file:excerpt.sql then the prompt.
  6. Score each answer against the code yourself (you know the right answer — that is the point). Fill in the table.
PYTHON — token estimator (pip install tiktoken)
# count_tokens.py  — rough estimate; Copilot models use their own tokenisers,
# but o200k_base is close enough to compare A vs B vs C.
import sys, tiktoken
enc = tiktoken.get_encoding("o200k_base")
for path in sys.argv[1:]:
    text = open(path, encoding="utf-8", errors="ignore").read()
    n = len(enc.encode(text))
    print(f"{path:40s} lines={text.count(chr(10))+1:5d}  chars={len(text):7d}  tokens≈{n}")

# usage:
#   python count_tokens.py usp_Load_PolicyPremium.sql excerpt.sql

Record your results

for i in 1 2 3 4 5 6 7; do
  DAY=$(date -u -d "-$i day" +%F)          # macOS: date -u -v-${i}d +%F

  gh api -H "X-GitHub-Api-Version: 2026-03-10" \
    "/orgs/$ORG/copilot/metrics/reports/organization-1-day?day=$DAY" \

# Inspect the field names FIRST — don't guess them:

8Fabric Workspace Connection — Git Round Trip

0:45 – 1:30 · 45 min · work in pairs: one person in Fabric, one in VS Code/GitHub, then swap

8.1 Mental model

A Fabric workspace connected to Git is a two-way mirror of item definitions (notebooks, pipelines, semantic models, reports, lakehouse/warehouse metadata). It is not a backup of data — lakehouse files and table rows never go into Git.

DirectionFabric buttonGit equivalent
Workspace → GitSource control → Changes → Commitcommit + push
Git → WorkspaceSource control → Updates → Update allpull

8.2 Prerequisites

  • Workspace on a Fabric capacity (Git integration is not available on Pro-only workspaces).
  • Tenant switches enabled in the Admin portal (Git integration; GitHub integration if using GitHub) — or delegated to capacity/workspace admins.
  • You are Admin of the workspace to connect (only Admins can connect, sync settings, or disconnect).
  • A repo in GitHub or Azure DevOps where you have write access. An empty repo or an empty folder is easiest.
  • GitHub: a fine-grained PAT scoped to the repo with Contents: Read and write (or use the GitHub account connection offered in Fabric).

8.3 Connect (Admin, ~8 min)

  1. Open the workspace → Workspace settings → Git integration.
  2. Choose provider: GitHub or Azure DevOps.
  3. GitHub: Add account → Display name gh-<yourname>, paste PAT, repository URL https://github.com/<org>/<repo> → Add.
    Azure DevOps: sign in with your Entra ID account → pick Organization, Project, Repository.
  4. Branch: main (or create dev-<yourname> for the lab — recommended).
  5. Git folder: fabric/ (keeps the repo root clean). Click Connect and sync.
  6. If both sides have content Fabric asks which way to sync first. Read the dialog — choosing the wrong direction overwrites the other side.
✅ Check The workspace header shows the branch name and a Source control button; every item shows a Git status of Synced. In the repo you see a folder per item, e.g. fabric/NB_PolicyLoad.Notebook/ containing .platform and notebook-content.py.

8.4 The round trip (~25 min)

Step 1 — PULL (Git → Fabric baseline)

  1. Click Source control. On the Updates tab, if anything is listed click Update all. Note the commit ID shown at the bottom of the panel.

Step 2 — CHANGE in Fabric

  1. Open notebook NB_PolicyLoad (create it if empty). Add a cell:
PYSPARK — cell to add
# Round-trip marker — changed in Fabric
LOAD_TYPE = "INCREMENTAL"   # never default to FULL (see Module 11)
print(f"Round trip test, load type = {LOAD_TYPE}")

Step 3 — PUSH (Fabric → Git)

  1. Source control → Changes tab → item shows Modified → tick it → commit message M8: add load-type marker (Fabric side) → Commit.
  2. Partner opens the repo on GitHub/ADO and confirms the commit and the diff in notebook-content.py.

Step 4 — CHANGE in Git (outside Fabric)

BASH — partner edits in VS Code
git clone https://github.com//.git && cd 
git checkout dev-
code fabric/NB_PolicyLoad.Notebook/notebook-content.py
#   change the print line to:  print(f"Round trip OK (edited in Git), load type = {LOAD_TYPE}")
git add . && git commit -m "M8: edit notebook from VS Code (Git side)"
git push

Step 5 — SYNC BACK (Git → Fabric)

  1. Back in Fabric, Source control → Updates → the notebook shows an incoming change → Update all.
  2. Open the notebook — the edited print line is there. Run the cell.
✅ Success check Two commits in history (one from Fabric, one from VS Code), the notebook in Fabric shows the Git-side edit, and the item status is Synced.

9Authentication & Permissions Mechanics

1:30 – 1:50 · 20 min

9.1 The key idea: two permission systems must both say yes

What a person can do = Fabric workspace role ∩ Git provider permission. Being a workspace Admin doesn't let you push to a protected branch; being a repo maintainer doesn't let you commit from Fabric if you're only a Viewer.

OperationFabric role needed
Connect / disconnect workspace to Git, change sync settingsAdmin
Switch branch / create branch from FabricAdmin (or Member/Contributor with write on all items, if the workspace setting "Allow users with at least Contributor role to change Git branch" is ON)
Commit and updateContributor+ with write permission on the items, plus write access in Git
View Git status & connection detailsAdmin, Member, Contributor
Branch out to another workspaceAdmin, Member, Contributor
ViewerCannot use Git integration
Upcoming change — tell learners Microsoft's docs state that from 1 December 2026, users without read-write permission on workspace items can't use Git integration. Audit any "read-only but commits sometimes" users now.

10When NOT to Use AI (Unsupervised)

1:50 – 2:10 · 20 min · 5 min framing + 10 min individual + 5 min share

10.1 The test — use AI unsupervised only if ALL four are "yes"

QuestionIf "no" →
1. Can I verify the output faster than I could write it?You'll trust it blindly. Supervise or don't use.
2. Is the action reversible (no TRUNCATE/DELETE/DROP on real data, no external send)?Human runs it, after review.
3. Is the input free of PII/PHI and confidential data?Mask first, or don't paste.
4. Is the business rule written down somewhere the AI can see?It will invent one that sounds right.

11Do's and Don'ts for AI in Data Work

2:10 – 2:35 · 25 min · build a one-page card anchored on a real past bug

11.1 How to build the card (10 min)

  1. Write the bug in 3 lines: what happened, why, what it cost. (Use the Everguard FULL-load issue, or your own.)
  2. Ask: "Which single rule, if followed, would have prevented this?" — that becomes your #1 Don't.
  3. Fill the rest of the card with rules that are specific and checkable ("never default @LoadType to FULL") rather than slogans ("be careful").
  4. Keep it to one printed page. Pin it in the repo as docs/AI-DATA-CARD.md and copy the top rules into .github/copilot-instructions.md so Copilot sees them too.

11.2 Sample card (edit the bug box with your real details)

AI in Insurance Data Work — Do / Don't

✔ DO

  • Scope prompts to the block you're changing (#file, selection).
  • Give the AI the business rule in writing (load type, SCD type, grain, keys).
  • Ask for a diff and read every changed line.
  • Run AI code first on a DEV copy with a row-count before/after.
  • Make load procs idempotent — running twice gives the same result.
  • Test the empty source, NULL keys, duplicate keys, equal-timestamp cases.
  • Mask policy numbers, names, DOB, claim notes before pasting samples.
  • Record the prompt + model in the PR description.

✘ DON'T

  • Don't let a load default to FULL. FULL must be explicit, logged and guarded.
  • Don't accept any TRUNCATE/DELETE without a guard (source row count > 0, environment check).
  • Don't run agent mode against prod connections.
  • Don't paste raw claims/policy data or connection strings into chat.
  • Don't let AI invent premium, reserve or commission formulas.
  • Don't merge AI SQL that you haven't executed against test data.
  • Don't "fix" a failing test by changing the test.

Root cause: load-type parameter defaulted to FULL / was not passed by the caller; no guard on the delete step.
Impact: ____ rows affected, ____ hours to recover, downstream reports wrong for ____.
Rule it created: FULL loads require an explicit parameter + a source-row-count guard + a log entry.
Honest caveat I don't have the actual Everguard incident details — the bug box is a structured placeholder based on the description "FULL-load issue". Learners should fill in the real cause and impact; a card based on a guessed bug teaches the wrong rule.
MARKDOWN — paste top rules into .github/copilot-instructions.md
## Data load rules (insurance warehouse)
- Load procedures take an explicit @LoadType parameter with NO default. Valid values: 'FULL', 'INCREMENTAL'.
- Never generate TRUNCATE or unfiltered DELETE without a preceding guard that the source has > 0 rows.
- Incremental filters use the stored watermark with >= and de-duplicate on the business key, not >.
- All procs must be idempotent and wrapped in BEGIN TRY / BEGIN TRAN ... COMMIT / CATCH ROLLBACK.
- Do not invent premium, reserve, or commission formulas; ask for the rule if it is not in the prompt.
- Never include sample data containing names, policy numbers, DOB or claim notes.

12.2 The AI-generated proc under test

This is what Copilot produced for: "Write a stored procedure that loads policy premiums from staging into the fact table, supporting full and incremental loads." It looks fine. It has two real bugs.

T-SQL — AI-generated (as received)
CREATE OR ALTER PROCEDURE dbo.usp_Load_PolicyPremium
    @LoadType VARCHAR(20) = 'FULL'               -- ⚠ bug 1: defaults to FULL
AS
BEGIN
    SET NOCOUNT ON;
    DECLARE @Watermark DATETIME2 =
        (SELECT ISNULL(MAX(LastLoadedAt),'1900-01-01') FROM dbo.LoadWatermark WHERE TableName = 'FactPolicyPremium');

    IF @LoadType = 'FULL'
    BEGIN
        DELETE FROM dbo.FactPolicyPremium;        -- ⚠ no guard: wipes target even if staging is empty
        INSERT INTO dbo.FactPolicyPremium (PolicyNo, PremiumAmt, EffectiveDate, UpdatedAt)
        SELECT PolicyNo, PremiumAmt, EffectiveDate, UpdatedAt FROM stg.PolicyPremium;
    END
    ELSE
    BEGIN
        INSERT INTO dbo.FactPolicyPremium (PolicyNo, PremiumAmt, EffectiveDate, UpdatedAt)
        SELECT PolicyNo, PremiumAmt, EffectiveDate, UpdatedAt
        FROM stg.PolicyPremium
        WHERE UpdatedAt > @Watermark;            -- ⚠ bug 2: rows with UpdatedAt = watermark are skipped;
                                                  --          updated policies are inserted again (duplicates)
    END

    UPDATE dbo.LoadWatermark SET LastLoadedAt = (SELECT MAX(UpdatedAt) FROM stg.PolicyPremium)
    WHERE TableName = 'FactPolicyPremium';       -- ⚠ sets NULL if staging empty; no transaction
END
Platform note Written in plain T-SQL that runs on SQL Server, Azure SQL and Fabric Warehouse. Fabric Warehouse has some T-SQL surface differences (e.g., certain constraints and features are limited) — if a statement fails there, that is itself a finding to record.

12.4 Corrected procedure (re-run the same tests → all PASS)

T-SQL — fixed
CREATE OR ALTER PROCEDURE dbo.usp_Load_PolicyPremium
    @LoadType VARCHAR(20)                         -- no default: caller must choose
AS
BEGIN
    SET NOCOUNT ON;
    IF @LoadType NOT IN ('FULL','INCREMENTAL')
        THROW 50001, 'Invalid @LoadType. Use FULL or INCREMENTAL.', 1;

    DECLARE @SrcRows INT = (SELECT COUNT(*) FROM stg.PolicyPremium);
    IF @SrcRows = 0
    BEGIN
        PRINT 'Staging empty - nothing loaded, target and watermark unchanged.';
        RETURN;
    END

    DECLARE @Watermark DATETIME2(0) =
        (SELECT ISNULL(MAX(LastLoadedAt),'1900-01-01') FROM dbo.LoadWatermark WHERE TableName='FactPolicyPremium');

    BEGIN TRY
        BEGIN TRAN;

        IF @LoadType = 'FULL'
        BEGIN
            DELETE FROM dbo.FactPolicyPremium;
            INSERT INTO dbo.FactPolicyPremium (PolicyNo, PremiumAmt, EffectiveDate, UpdatedAt)
            SELECT PolicyNo, PremiumAmt, EffectiveDate, UpdatedAt FROM stg.PolicyPremium;
        END
        ELSE
        BEGIN
            -- latest version per policy at or after the watermark
            ;WITH src AS (
                SELECT PolicyNo, PremiumAmt, EffectiveDate, UpdatedAt,
                       ROW_NUMBER() OVER (PARTITION BY PolicyNo ORDER BY UpdatedAt DESC) AS rn
                FROM stg.PolicyPremium
                WHERE UpdatedAt >= @Watermark
            )
            SELECT PolicyNo, PremiumAmt, EffectiveDate, UpdatedAt INTO #delta FROM src WHERE rn = 1;

            UPDATE f SET f.PremiumAmt = d.PremiumAmt, f.EffectiveDate = d.EffectiveDate, f.UpdatedAt = d.UpdatedAt
            FROM dbo.FactPolicyPremium f JOIN #delta d ON f.PolicyNo = d.PolicyNo;

            INSERT INTO dbo.FactPolicyPremium (PolicyNo, PremiumAmt, EffectiveDate, UpdatedAt)
            SELECT d.PolicyNo, d.PremiumAmt, d.EffectiveDate, d.UpdatedAt
            FROM #delta d
            WHERE NOT EXISTS (SELECT 1 FROM dbo.FactPolicyPremium f WHERE f.PolicyNo = d.PolicyNo);
        END

        UPDATE dbo.LoadWatermark
           SET LastLoadedAt = (SELECT MAX(UpdatedAt) FROM stg.PolicyPremium)
         WHERE TableName = 'FactPolicyPremium';

        COMMIT;
    END TRY
    BEGIN CATCH
        IF @@TRANCOUNT > 0 ROLLBACK;
        THROW;
    END CATCH
END
Gotcha in the fix Using >= means the last row at the watermark is re-read every run. That's safe only because the incremental branch upserts by PolicyNo — T5 proves it. Change one without the other and you get duplicates back.
