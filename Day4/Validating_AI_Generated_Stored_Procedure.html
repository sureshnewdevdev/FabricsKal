1Why "it looks right" isn't validation

0:00 – 0:03

AI-generated SQL fails in a predictable way. It handles the happy path perfectly and quietly gets the edges wrong. Those edges are empty sources, equal timestamps, duplicate keys, bad parameters and mid-load failures. In data loads, edge-case bugs don't throw errors. They delete or duplicate rows silently, and you find out from a business user days later.

Compiles→Matches the rule→Happy path→Edge cases→Failure & rollback→Operability

Most people stop at step 3. Today's proc passes step 3 and fails almost everything after it.

Rule for the session A human writes the expected results. You may ask Copilot to help write test code, but if the AI that wrote the proc also decides what "correct" means, it is grading its own homework.

2The AI-generated procedure under test

0:03 – 0:06

This is the prompt that produced it:

PROMPT given to Copilot
Write a T-SQL stored procedure dbo.usp_Load_PolicyPremium that loads policy
premiums from stg.PolicyPremium into dbo.FactPolicyPremium. It should support
FULL and INCREMENTAL loads. Incremental loads use a watermark stored in
dbo.LoadWatermark (TableName, LastLoadedAt). Update the watermark after loading.
Why we use a fixed "as received" version If every learner regenerates it, everyone gets slightly different code and the expected results won't line up. Use this baseline in class. As homework, regenerate with your own model and run the same harness. Comparing the results is a great discussion.
T-SQL — AI version (as received) · create this first
CREATE OR ALTER PROCEDURE dbo.usp_Load_PolicyPremium
    @LoadType VARCHAR(20) = 'FULL'
AS
BEGIN
    SET NOCOUNT ON;

    DECLARE @Watermark DATETIME2(0) =
        (SELECT ISNULL(MAX(LastLoadedAt), '1900-01-01')
         FROM dbo.LoadWatermark WHERE TableName = 'FactPolicyPremium');

    IF @LoadType = 'FULL'
    BEGIN
        DELETE FROM dbo.FactPolicyPremium;
        INSERT INTO dbo.FactPolicyPremium (PolicyNo, PremiumAmt, EffectiveDate, UpdatedAt)
        SELECT PolicyNo, PremiumAmt, EffectiveDate, UpdatedAt
        FROM stg.PolicyPremium;
    END
    ELSE
    BEGIN
        INSERT INTO dbo.FactPolicyPremium (PolicyNo, PremiumAmt, EffectiveDate, UpdatedAt)
        SELECT PolicyNo, PremiumAmt, EffectiveDate, UpdatedAt
        FROM stg.PolicyPremium
        WHERE UpdatedAt > @Watermark;
    END

    UPDATE dbo.LoadWatermark
       SET LastLoadedAt = (SELECT MAX(UpdatedAt) FROM stg.PolicyPremium)
     WHERE TableName = 'FactPolicyPremium';
END

3Build the checklist: derive tests from the code

DELETE / TRUNCATEWhat if the source is empty? What if the next step fails?T2, T9

4Turning a real past bug into a test

The most valuable test in any checklist is the one that reproduces something that already hurt you. Use this four-line conversion:

TEMPLATE — incident → test
INCIDENT   : Everguard policy load ran as FULL instead of INCREMENTAL;
             target was cleared and reloaded.            ← replace with real details
TRIGGER    : load-type parameter not passed / defaulted to FULL,
             and staging was empty or partial at run time.
EXPECTED   : a load must never reduce the target when the source has no valid rows,
             and FULL must never happen unless explicitly requested.
ASSERTION  : run proc with NO @LoadType and EMPTY staging
             → target row count unchanged (T2) and watermark unchanged (T3).
Honest caveat I don't have the actual Everguard incident details, so the trigger above is a structured guess based on "FULL-load issue". If the real cause was different (for example, a pipeline variable overriding the parameter, or a partial staging file), change T2's setup to reproduce that condition. A test for a guessed bug protects against the wrong thing.

Other real-bug patterns worth converting from your team's history:

  • A file arrived twice, so premiums were double-counted. Test: the same batch loaded twice gives the same totals.
  • Timezone shift on UpdatedAt, so rows were skipped. Test: a row at the watermark in a different offset.
  • A source column was widened, so the insert failed halfway. Test: T9 (overflow mid-load).

6Run the harness against the AI version

0:12 – 0:20

The harness is one batch (no GO inside), so variables survive between tests. Every proc call is wrapped in TRY/CATCH, so one failing test can't stop the rest. The only thing you change between runs is @Run.

T-SQL — test harness (run as ONE batch)
DECLARE @Run VARCHAR(30) = 'AI-v1';     -- ← change to 'Fixed-v2' after Section 7
DECLARE @n INT, @nNull INT, @amt DECIMAL(14,2), @wm DATETIME2(0), @err NVARCHAR(4000);

DELETE FROM dbo.TestResults WHERE RunLabel = @Run;   -- clean re-run

--------------------------------------------------------------------------
-- T1  Happy path: incremental loads 3 new rows
--------------------------------------------------------------------------
DELETE FROM stg.PolicyPremium; DELETE FROM dbo.FactPolicyPremium; DELETE FROM dbo.LoadWatermark;
INSERT INTO dbo.LoadWatermark VALUES ('FactPolicyPremium', '2026-10-01 00:00:00');
INSERT INTO stg.PolicyPremium VALUES
 ('P001', 1200.00, '2026-10-01', '2026-10-02 09:00:00'),
 ('P002',  850.50, '2026-10-01', '2026-10-02 09:00:00'),
 ('P003',  990.00, '2026-10-01', '2026-10-03 10:00:00');
SET @err = NULL;
BEGIN TRY EXEC dbo.usp_Load_PolicyPremium @LoadType = 'INCREMENTAL'; END TRY
BEGIN CATCH SET @err = ERROR_MESSAGE(); END CATCH;
SELECT @n = COUNT(*) FROM dbo.FactPolicyPremium;
INSERT INTO dbo.TestResults VALUES (@Run, SYSDATETIME(), 'T1', 'Happy path: incremental loads new rows',
  '3 rows', CONCAT(@n, ' rows', ISNULL(' | err: ' + @err, '')),
  CASE WHEN @n = 3 AND @err IS NULL THEN 'PASS' ELSE 'FAIL' END);

--------------------------------------------------------------------------
-- T2  REAL-BUG EDGE CASE (Everguard pattern):
--     caller omits @LoadType AND staging is empty → target must be untouched
--------------------------------------------------------------------------
DELETE FROM stg.PolicyPremium;                    -- staging empty, fact still has 3 rows from T1
SET @err = NULL;
BEGIN TRY EXEC sp_executesql N'EXEC dbo.usp_Load_PolicyPremium;'; END TRY   -- no parameter
BEGIN CATCH SET @err = ERROR_MESSAGE(); END CATCH;
SELECT @n = COUNT(*) FROM dbo.FactPolicyPremium;
INSERT INTO dbo.TestResults VALUES (@Run, SYSDATETIME(), 'T2', 'REAL BUG: no @LoadType + empty staging keeps target',
  '3 rows', CONCAT(@n, ' rows', ISNULL(' | err: ' + LEFT(@err, 80), '')),
  CASE WHEN @n = 3 THEN 'PASS' ELSE 'FAIL' END);

--------------------------------------------------------------------------
-- T3  Watermark not NULL and not moved by the empty run
--------------------------------------------------------------------------
SELECT @wm = LastLoadedAt FROM dbo.LoadWatermark WHERE TableName = 'FactPolicyPremium';
INSERT INTO dbo.TestResults VALUES (@Run, SYSDATETIME(), 'T3', 'Watermark unchanged after empty run',
  '2026-10-03 10:00:00', ISNULL(CONVERT(VARCHAR(19), @wm, 120), 'NULL'),
  CASE WHEN @wm = '2026-10-03 10:00:00' THEN 'PASS' ELSE 'FAIL' END);

--------------------------------------------------------------------------
-- T4  Boundary: late row stamped EXACTLY at the watermark must load
--------------------------------------------------------------------------
DELETE FROM stg.PolicyPremium; DELETE FROM dbo.FactPolicyPremium;
UPDATE dbo.LoadWatermark SET LastLoadedAt = '2026-10-03 10:00:00';
INSERT INTO stg.PolicyPremium VALUES ('P004', 700.00, '2026-10-03', '2026-10-03 10:00:00');
SET @err = NULL;
BEGIN TRY EXEC dbo.usp_Load_PolicyPremium @LoadType = 'INCREMENTAL'; END TRY
BEGIN CATCH SET @err = ERROR_MESSAGE(); END CATCH;
SELECT @n = COUNT(*) FROM dbo.FactPolicyPremium WHERE PolicyNo = 'P004';
INSERT INTO dbo.TestResults VALUES (@Run, SYSDATETIME(), 'T4', 'Boundary: equal-timestamp late row loads',
  '1 row', CONCAT(@n, ' rows'), CASE WHEN @n = 1 THEN 'PASS' ELSE 'FAIL' END);

--------------------------------------------------------------------------
-- T5  Changed policy is UPDATED; running twice creates no duplicates
--------------------------------------------------------------------------
DELETE FROM stg.PolicyPremium; DELETE FROM dbo.FactPolicyPremium;
UPDATE dbo.LoadWatermark SET LastLoadedAt = '2026-10-01 00:00:00';
INSERT INTO dbo.FactPolicyPremium VALUES ('P001', 1200.00, '2026-10-01', '2026-09-30 09:00:00');
INSERT INTO stg.PolicyPremium     VALUES ('P001', 1350.00, '2026-10-01', '2026-10-04 09:00:00');
SET @err = NULL;
BEGIN TRY
  EXEC dbo.usp_Load_PolicyPremium @LoadType = 'INCREMENTAL';
  EXEC dbo.usp_Load_PolicyPremium @LoadType = 'INCREMENTAL';   -- re-run
END TRY
BEGIN CATCH SET @err = ERROR_MESSAGE(); END CATCH;
SELECT @n = COUNT(*), @amt = MAX(PremiumAmt) FROM dbo.FactPolicyPremium WHERE PolicyNo = 'P001';
INSERT INTO dbo.TestResults VALUES (@Run, SYSDATETIME(), 'T5', 'Update applied, idempotent on re-run',
  '1 row @ 1350.00', CONCAT(@n, ' row(s) @ ', @amt),
  CASE WHEN @n = 1 AND @amt = 1350.00 THEN 'PASS' ELSE 'FAIL' END);

--------------------------------------------------------------------------
-- T6  Two versions of the same policy in ONE batch → keep latest
--------------------------------------------------------------------------
DELETE FROM stg.PolicyPremium; DELETE FROM dbo.FactPolicyPremium;
UPDATE dbo.LoadWatermark SET LastLoadedAt = '2026-10-01 00:00:00';
INSERT INTO stg.PolicyPremium VALUES
 ('P010', 500.00, '2026-10-05', '2026-10-05 08:00:00'),
 ('P010', 550.00, '2026-10-05', '2026-10-05 09:00:00');
SET @err = NULL;
BEGIN TRY EXEC dbo.usp_Load_PolicyPremium @LoadType = 'INCREMENTAL'; END TRY
BEGIN CATCH SET @err = ERROR_MESSAGE(); END CATCH;
SELECT @n = COUNT(*), @amt = MAX(PremiumAmt) FROM dbo.FactPolicyPremium WHERE PolicyNo = 'P010';
INSERT INTO dbo.TestResults VALUES (@Run, SYSDATETIME(), 'T6', 'Duplicate versions in batch: latest wins',
  '1 row @ 550.00', CONCAT(@n, ' row(s) @ ', @amt),
  CASE WHEN @n = 1 AND @amt = 550.00 THEN 'PASS' ELSE 'FAIL' END);

--------------------------------------------------------------------------
-- T7  NULL business key is rejected, valid row still loads
--------------------------------------------------------------------------
DELETE FROM stg.PolicyPremium; DELETE FROM dbo.FactPolicyPremium;
UPDATE dbo.LoadWatermark SET LastLoadedAt = '2026-10-01 00:00:00';
INSERT INTO stg.PolicyPremium VALUES
 (NULL,   100.00, '2026-10-05', '2026-10-05 10:00:00'),
 ('P020', 200.00, '2026-10-05', '2026-10-05 10:00:00');
SET @err = NULL;
BEGIN TRY EXEC dbo.usp_Load_PolicyPremium @LoadType = 'INCREMENTAL'; END TRY
BEGIN CATCH SET @err = ERROR_MESSAGE(); END CATCH;
SELECT @nNull = COUNT(*) FROM dbo.FactPolicyPremium WHERE PolicyNo IS NULL;

INSERT INTO dbo.TestResults VALUES (@Run, SYSDATETIME(), 'T7', 'NULL key rejected, valid row loaded',
  '0 null / 1 valid', CONCAT(@nNull, ' null / ', @n, ' valid'),
  CASE WHEN @nNull = 0 AND @n = 1 THEN 'PASS' ELSE 'FAIL' END);

--------------------------------------------------------------------------
-- T8  Invalid @LoadType must raise an error (not run silently)
--------------------------------------------------------------------------
SET @err = NULL;
BEGIN TRY EXEC dbo.usp_Load_PolicyPremium @LoadType = 'FUL'; END TRY      -- typo
BEGIN CATCH SET @err = ERROR_MESSAGE(); END CATCH;
INSERT INTO dbo.TestResults VALUES (@Run, SYSDATETIME(), 'T8', 'Invalid @LoadType raises error',
  'error raised', ISNULL(LEFT(@err, 80), 'no error'),
  CASE WHEN @err IS NOT NULL THEN 'PASS' ELSE 'FAIL' END);

--------------------------------------------------------------------------
-- T9  FULL load hits a bad row mid-insert → everything rolls back
--------------------------------------------------------------------------
DELETE FROM stg.PolicyPremium; DELETE FROM dbo.FactPolicyPremium;
INSERT INTO dbo.FactPolicyPremium VALUES
 ('P100', 1000.00, '2026-10-01', '2026-10-01 09:00:00'),
 ('P101', 1100.00, '2026-10-01', '2026-10-01 09:00:00');
INSERT INTO stg.PolicyPremium VALUES
 ('P100', 1000.00,        '2026-10-06', '2026-10-06 09:00:00'),
 ('P102', 99999999999.99, '2026-10-06', '2026-10-06 09:00:00');   -- overflows DECIMAL(12,2)
SET @err = NULL;
BEGIN TRY EXEC dbo.usp_Load_PolicyPremium @LoadType = 'FULL'; END TRY
BEGIN CATCH SET @err = ERROR_MESSAGE(); END CATCH;
SELECT @n = COUNT(*) FROM dbo.FactPolicyPremium WHERE PolicyNo IN ('P100', 'P101');
INSERT INTO dbo.TestResults VALUES (@Run, SYSDATETIME(), 'T9', 'Mid-load failure rolls back (FULL)',
  '2 original rows + error', CONCAT(@n, ' rows', ISNULL(' | err: ' + LEFT(@err, 60), ' | no error')),
  CASE WHEN @n = 2 AND @err IS NOT NULL THEN 'PASS' ELSE 'FAIL' END);

--------------------------------------------------------------------------

7Apply the fix and re-run

0:20 – 0:24
T-SQL — fixed version
CREATE OR ALTER PROCEDURE dbo.usp_Load_PolicyPremium
    @LoadType VARCHAR(20)                -- NO default: the caller must choose explicitly
AS
BEGIN
    SET NOCOUNT ON;

    -- 1. Validate the parameter (fixes T8)
    IF @LoadType IS NULL OR @LoadType NOT IN ('FULL', 'INCREMENTAL')
        THROW 50001, 'Invalid @LoadType. Pass FULL or INCREMENTAL explicitly.', 1;

    DECLARE @Watermark DATETIME2(0) =
        (SELECT ISNULL(MAX(LastLoadedAt), '1900-01-01')
         FROM dbo.LoadWatermark WHERE TableName = 'FactPolicyPremium');

    -- 2. Build a clean delta: valid keys only (T7), latest version per policy (T6),
    --    boundary-inclusive filter for incremental (T4)
    DROP TABLE IF EXISTS #delta;

    SELECT PolicyNo, PremiumAmt, EffectiveDate, UpdatedAt
    INTO #delta
    FROM (
        SELECT PolicyNo, PremiumAmt, EffectiveDate, UpdatedAt,
               ROW_NUMBER() OVER (PARTITION BY PolicyNo ORDER BY UpdatedAt DESC) AS rn
        FROM stg.PolicyPremium
        WHERE PolicyNo IS NOT NULL
          AND (@LoadType = 'FULL' OR UpdatedAt >= @Watermark)
    ) s
    WHERE rn = 1;

    -- 3. Guard: nothing valid to load → change nothing (fixes T2, T3)
    IF NOT EXISTS (SELECT 1 FROM #delta)
    BEGIN
        PRINT 'No valid source rows - target and watermark left unchanged.';
        RETURN;
    END

    DECLARE @NewWatermark DATETIME2(0) = (SELECT MAX(UpdatedAt) FROM #delta);

    -- 4. All-or-nothing (fixes T9)
    BEGIN TRY
        BEGIN TRAN;

        IF @LoadType = 'FULL'
        BEGIN
            DELETE FROM dbo.FactPolicyPremium;
            INSERT INTO dbo.FactPolicyPremium (PolicyNo, PremiumAmt, EffectiveDate, UpdatedAt)
            SELECT PolicyNo, PremiumAmt, EffectiveDate, UpdatedAt FROM #delta;
        END
        ELSE
        BEGIN
            -- upsert by business key (fixes T5)
            UPDATE f
               SET f.PremiumAmt    = d.PremiumAmt,
                   f.EffectiveDate = d.EffectiveDate,
                   f.UpdatedAt     = d.UpdatedAt
              FROM dbo.FactPolicyPremium f
              JOIN #delta d ON f.PolicyNo = d.PolicyNo;

            INSERT INTO dbo.FactPolicyPremium (PolicyNo, PremiumAmt, EffectiveDate, UpdatedAt)
            SELECT d.PolicyNo, d.PremiumAmt, d.EffectiveDate, d.UpdatedAt
            FROM #delta d
            WHERE NOT EXISTS (SELECT 1 FROM dbo.FactPolicyPremium f WHERE f.PolicyNo = d.PolicyNo);
        END

        -- watermark never NULL, never moves backwards on incremental
        UPDATE dbo.LoadWatermark
           SET LastLoadedAt = CASE
                 WHEN @LoadType = 'FULL' THEN @NewWatermark
                 WHEN @NewWatermark > ISNULL(LastLoadedAt, '1900-01-01') THEN @NewWatermark
                 ELSE LastLoadedAt END
         WHERE TableName = 'FactPolicyPremium';

        COMMIT;
    END TRY
    BEGIN CATCH
        IF @@TRANCOUNT > 0 ROLLBACK;
        THROW;
    END CATCH
END

Gotcha inside the fix The >= filter re-reads the last row at the watermark on every run. That is only safe because the incremental branch upserts by PolicyNo, which T5 proves. If someone later "optimises" the upsert back to INSERT-only, T5 fails. That is exactly why the test stays in the suite.

!Gotchas & extensions

GotchaWhat to do
Harness stops at the first errorYou split it with GO or ran only part of it. Run it as one batch. Every EXEC is wrapped in TRY/CATCH.
T2 on the fixed version shows an error messageThat's expected. The proc now refuses to run without @LoadType. The test passes because the target is untouched.
Fabric Warehouse rejects a statementThe Fabric Warehouse T-SQL surface differs from SQL Server in places (temp tables, some DML and constraint features). Record it as a finding, then try the same harness on SQL Server or Azure SQL to separate "platform limitation" from "logic bug".
Copilot "fixes" a failing test by changing the expected valueReject it. Expected values come from the business rule, not from the code's current behaviour.
All tests pass on your own regenerated procGood, but check that your tests can still fail. Temporarily break one line (e.g., >= → >) and confirm T4 goes red.

Using Copilot as a second reviewer (not as the judge)

PROMPT — after your own review, with #file pointing at the proc
Review #file:usp_Load_PolicyPremium.sql against these rules. For each rule,
answer PASS / FAIL / UNSURE and quote the exact line number. Do not rewrite the code.
1. @LoadType has no default and invalid values raise an error.
2. No DELETE/TRUNCATE can run when the source has zero valid rows.
3. Delete + insert happen inside one transaction with rollback on error.
4. Incremental filter includes rows equal to the watermark.
5. Incremental load updates existing keys and never duplicates them.
6. NULL business keys are excluded.
7. Watermark can never become NULL or move backwards.
Then list any edge case I have NOT covered.

The last line is the useful one. AI is decent at suggesting extra edge cases. A human still decides whether each one matters and what the correct expected result is.

Extensions (homework)

  • M3 performance: seed 1M staging rows with a numbers CTE and time both versions. The ROW_NUMBER and upsert cost something, so record it.
  • Safety ratio for FULL: add a guard that refuses a FULL load when the delta is smaller than X% of the current target, and add a test for it.
  • Automate: wrap the harness in a pipeline step or a GitHub Action against a DEV database, so every PR touching the proc runs T1–T9.
  • tSQLt: on SQL Server / Azure SQL, port the tests to the tSQLt framework for proper isolation with fake tables.
